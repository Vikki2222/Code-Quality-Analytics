# Chronicles

An AI-powered engineering intelligence platform that transforms individual GitHub PR reviews into persistent, structured findings — tracking recurring issues, code quality hotspots, and engineering trends across a repository over time.

> **The core idea:** Most AI code review tools treat each PR in isolation. This platform stores structured findings across many PRs and builds a historical memory of your codebase — answering *"what keeps going wrong, and are we actually getting better?"*

---

## What it does

1. Connect your GitHub account via OAuth
2. Select any repository and pull request
3. The platform fetches the PR diff, filters noise (vendored files, lock files, binaries), and sends only the relevant code to an AI model
4. Findings are returned as structured JSON (category, severity, file, line, description, recommendation)
5. Each finding is fingerprinted — future occurrences of the same issue are recognized and linked, not stored as duplicates
6. Over time, the platform surfaces recurring problems, file hotspots, issue trends, and a calculated repository health score

## Architecture

```
React Frontend (Vite + Tailwind)
        │
        │ HTTP + session cookie
        ▼
Express API Server
  ├── GitHub OAuth (Passport.js)
  ├── GitHub REST API (repos, PRs, diffs)
  ├── POST /api/reviews → enqueue job → return { reviewId, status: "queued" }
  ├── GET  /api/reviews/:id → poll for status/findings
  ├── GET  /api/analytics/:owner/:repo/dashboard
  └── POST /api/webhooks/github → HMAC-verified auto-trigger
        │
        ▼
Redis + BullMQ (review-analysis queue)
        │
        ▼
Background Worker (separate Node.js process)
  ├── Fetch PR diff via GitHub API
  ├── Filter/rank/budget files (diffBudget.js)
  ├── Call LLM via OpenRouter → structured findings JSON
  ├── Two-tier fingerprinting (structural hash → embedding similarity)
  └── Persist to PostgreSQL (findings, fingerprints, lifecycle status)
        │
        ▼
PostgreSQL
  └── users · pull_requests · reviews · findings · finding_fingerprints · webhook_deliveries
```

## Key engineering decisions

### Async job architecture
`POST /api/reviews` immediately returns `{ reviewId, status: "queued" }` — it never blocks waiting for GitHub or the AI. BullMQ handles the actual work in a separate worker process, with 3-attempt exponential backoff retry on failure. The frontend polls `GET /api/reviews/:id` every 2 seconds until completion.

### Two-tier fingerprinting
The core differentiator. When a finding is stored, it's assigned to a persistent fingerprint group so future occurrences of the same issue are recognized rather than duplicated:

- **Tier 1 — structural hash:** normalizes the finding title (lowercase, strip punctuation/numbers, remove stopwords, crude stem, sort tokens) and hashes `repo + file + category + normalized_title` with SHA-256. Fast, deterministic, no API calls. Catches near-identical rewordings.
- **Tier 2 — embedding similarity:** if Tier 1 misses, fetches a Gemini embedding for `title + description` and computes cosine similarity against existing fingerprints in the same `repo + file + category` bucket (threshold: 0.85). Catches genuine paraphrases Tier 1 can't normalize away.

Deliberately no LLM-as-judge for identity decisions — identity needs to be stable and cheap, not dependent on model mood.

### AI identifies, application calculates
The LLM finds issues. All metrics (health score, trend %, recurring counts) are calculated deterministically from stored data in application code — never generated by the AI. This keeps analytics auditable and reproducible.

### Repository health score
Starts at 100, penalized by open/recurring findings weighted by severity (`critical: -15`, `high: -8`, `medium: -4`, `low: -1`). Recurring issues apply a 1.5× multiplier (they've proven they don't get fixed). Resolved issues cost nothing. Calculated in `analytics.service.js`, not the LLM.

### Diff filtering before AI
A token budget pipeline runs before any AI call: filter out vendored/generated/binary files → rank remaining files by signal (lines changed × file type multiplier × historical hotspot boost) → greedily include files within a ~7,000-token budget → flag `partial_analysis: true` if anything was skipped. This prevents sending noise to the AI and keeps costs low.

### Security
- GitHub access tokens encrypted at rest with AES-256-GCM (authenticated encryption — tamper detection, not just encryption)
- Sessions backed by PostgreSQL via `connect-pg-simple` (survives server restarts; no in-memory store)
- Webhook payloads verified with HMAC-SHA256 + `timingSafeEqual` (prevents timing attacks)
- Rate limiting on all API endpoints (`express-rate-limit`), stricter limits on review creation
- Idempotency on webhook deliveries — duplicate GitHub retries don't create duplicate reviews
- Repo-level access control: history, analytics and review results are only returned if the user can see the repo on GitHub (checked with their token, cached 5 min)
- OAuth `state` parameter (login CSRF protection); tokens and OAuth codes are kept out of logs
- Access tokens are never placed in queue (Redis) job data — the worker loads them from the DB

## Local setup

### Quick start (Docker)

```bash
cp .env.example .env    # fill in the secrets; see comments in the file
docker compose up --build
```

App: `http://localhost`. Migrations run automatically when the API starts.
`docker-compose.override.yml` (local only) publishes ports 80 and 4000.
For production on Coolify, see [`docs/DEPLOYMENT.md`](docs/DEPLOYMENT.md).

### Without Docker

Prerequisites: Node.js 20+, PostgreSQL, Redis.

```bash
cd backend
npm install
cp ../.env.example .env
```

Fill in `.env` — `.env.example` documents every variable. The API and worker refuse
to start and list anything missing or malformed. For this setup use
`FRONTEND_URL=http://localhost:5173` and
`GITHUB_CALLBACK_URL=http://localhost:4000/api/auth/github/callback`.

Create the database (the schema is applied automatically: the API runs any pending
`backend/src/migrations/*.sql` files on startup):
```bash
createdb code_quality_analytics
```

Run the API server and worker in separate terminals:
```bash
npm run dev      # API server on port 4000
npm run worker   # BullMQ worker (separate process)
```

Run tests:
```bash
npm test
```

### Frontend

```bash
cd frontend
npm install
npm run dev      # Vite dev server on port 5173
```

Visit `http://localhost:5173`, click "Continue with GitHub".

### GitHub OAuth App setup
Create an OAuth App at `github.com/settings/developers`:
- Homepage URL: `http://localhost:5173`
- Authorization callback URL: `http://localhost:4000/api/auth/github/callback`

### Webhook setup (optional, for auto-trigger)
Expose your local server with `ngrok http 4000`, then register a webhook on any repo:
- Payload URL: `https://<ngrok-url>/api/webhooks/github`
- Content type: `application/json`
- Secret: matches `GITHUB_WEBHOOK_SECRET` in `.env`
- Events: Pull requests only

## Known limitations / deliberate tradeoffs

- **Fingerprint category scoping:** Tier 2 similarity is scoped per `repo + file + category`. If the AI categorizes the same underlying issue differently on separate runs (e.g., `readability` vs `maintainability`), fingerprinting won't merge them. Documented in `fingerprint.service.js`. Accepted tradeoff: the AI's categorization inconsistency is upstream of the matching logic.
- **Repo picker shows the 30 most recently pushed repos:** GitHub's `/user/repos` returns owned, collaborator and org-member repos; only the first page is loaded (no pagination UI yet).
- **Embeddings in JSONB, not pgvector:** At this scale (one user, handful of repos), comparing a few candidate embeddings in application code is fast enough. pgvector is the obvious next step if this scales to many repos/orgs.
- **Webhook user resolution by repo owner:** Webhooks look up the connected user whose GitHub account id matches the repo owner. Works for repos you own; org-owned repos never match (supporting them properly needs a GitHub App).
